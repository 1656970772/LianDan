## 3. 第一里程碑范围

### 3.1 本轮交付

本轮交付一个可在桌面 Chrome 中反复游玩的独立萃取闭环，包含：

- 8 种可替换的测试药材；
- 1 种火种；
- 1 个统一丹炉；
- 1 个基础接液容器；
- 药液、药渣、杂质三类精灵珠；
- 背包预选、取消、投药和多份药材不重叠自动排布；
- 固定火源、方向控制、火焰大小、炉温反馈；
- 二维绕流、动态障碍、局部溶解和成分图产珠；
- 精灵珠运动、碰撞、护盾、灼烧、推力、接取、落空和争斗；
- 药液流失、两级警告、失败转化、药渣结果物；
- 正常结束、失败、暂停、重开和“再来一炉”；
- 配置校验、调试面板、自动化测试和性能验收场景。

### 3.2 明确不做

以下内容不进入本轮代码：

- 融合与凝丹；
- 正式成丹结果、品质、残丹、废丹、异丹和炸炉；
- 丹方、快速炼制、产品级操作轨迹记录与重放；
- 玩家存档、localStorage、数据库和后端服务；
- 环境、天时、不同丹炉、炉内残留；
- 火种特殊能力；
- 丹纹、开放、密闭、泄压和手动分离；
- 触屏与移动端适配；
- 自动画质降级、自动删珠、合并真实珠子或跳过规则；
- 通用脚本规则引擎、ECS、Redux、XState、依赖注入容器等当前不需要的框架。

炉底药渣池和正常成丹时的药渣换算函数需要实现并测试，因为它们属于当前萃取结算；但本轮不展示正常成丹结果物。

## 4. 实施原则

### 4.1 规则与表现分离

- domain、simulation 和 application 不得引用 Phaser、DOM、window、资源 URL 或浏览器事件；
- game 只负责 Phaser 场景、渲染、声音、资源生命周期和视觉插值；
- ui 只负责原生 HTML/CSS 控件及其可访问状态；
- 浏览器输入先转为标准化命令，再进入应用层；
- Phaser Sprite 不能成为规则状态的唯一来源。

### 4.2 配置数据与算法分离

- 材料、初始库存、参数、布局、阈值、火种、珠子、容器、互动和主题都走配置；
- 稳定 ID、引用、默认值和合法范围不散落在场景代码中；
- 配置只选择程序支持的有限行为类型，不能执行任意脚本；
- 状态转移、体积守恒、阈值语义和模拟算法仍由代码保证，不把程序改造成配置解释器。

### 4.3 一个事实只有一个来源

- 成分图是材料内部三类成分分布的唯一来源；
- 目标珠子总数只用于换算标准珠体积，不再维护另一套固定产量；
- 火焰画面、药材溶解、珠子灼烧和火焰推力共同读取同一份火流结果；
- 流失率只由统一的体积台账计算；
- canFinish 是领域状态的派生值，不额外维护可失真的布尔缓存。

### 4.4 固定步长与可复现

- 规则与模拟默认按 30 Hz 固定 tick 推进，渲染帧率与规则帧率解耦；
- 60 FPS 画面在相邻模拟状态之间插值；
- 暂停和页面后台时不推进 tick，也不累计恢复后的补帧时间；
- domain 和 simulation 禁止直接使用 Date.now() 与 Math.random()；
- 所有会改变规则结果的随机数由可注入、可记录种子的 RandomSource 提供；
- 纯视觉随机与规则随机使用独立随机流，调整粒子效果不能改变结算。

### 4.5 先验证最高风险

二维绕流、动态障碍、局部溶解和 2400 珠性能是首要技术风险。它们必须在精致界面和完整美术之前通过技术门禁，避免后期推翻整套场景。

### 5.2 模块职责

| 模块 | 负责 | 明确不负责 |
| --- | --- | --- |
| application | 会话生命周期、固定 tick、命令队列、状态快照、事件缓冲、暂停恢复 | 具体规则、Phaser 对象、DOM |
| domain | 背包与投药状态、流程状态、炉温、体积台账、警告、失败、完成条件 | 绘制、真实时间、输入设备 |
| simulation | 火流、障碍栅格、溶解、产珠、运动、碰撞、推力、空间查询 | UI、音效、配置文件读取 |
| config | 加载、JSON Schema 校验、跨文件引用校验、资源语义校验、标准化 | 游戏规则判断 |
| game | Phaser 场景、Sprite 池、遮罩、粒子、声音、插值和镜头表现 | 修改领域规则 |
| ui | 背包、滑动条、按钮、Tips、弹板、调试面板 | 模拟和结算 |

状态所有权必须保持单写：simulation 独占材料格、珠子、障碍、位置、速度和互动计时器等模拟实体的可变事实；domain 独占库存、流程状态、炉温、体积台账、警告和结算事实；application 只负责编排命令、固定 tick 和两者间的原子提交。simulation 只能产出 `SimulationDelta`，不得直接改 domain 台账；domain 不得反向改模拟实体；application 和 game/ui 不得保存第二份可写规则状态。跨边界只传稳定 ID、命令、增量和只读快照，禁止用双写后“最终一致”的方式掩盖顺序问题。

### 5.3 应用层契约

浏览器适配器先把输入标准化为规则命令或应用控制，并按捕获顺序分配会话内从 1 开始连续递增的 `sequence`，不接受调用方自选或重复值。浏览器输入绝不在同步 tick 的 phase 0～10 内交付给 application；适配器只在相邻完整 tick 之间调用唯一入口 `beforePhase0(deliveryBoundaryTick)`。`deliveryBoundaryTick` 是下一次获准开始 phase 0 的待执行 tick；例如 tick 7 的 phase 0 已截取后才捕获的输入，只能在 tick 7 完整提交后的 `beforePhase0(8)` 交付。暂停时待执行 tick 不递增，因此该边界值保持不变，但 `beforePhase0` 和 control pump 仍可在每次应用调度时运行。

每个已接受输入持久化为 `InputLogEntry { sessionId, sequence, deliveryBoundaryTick, channel, envelope }`；需要读取浏览器生命周期事实的 focus/visibility、restart confirm 和“再来一炉”控制，其 payload 还必须保存捕获时的 `lifecycleSnapshot { hasFocus, visibilityState }`，实现读取当前 `document.hasFocus()`/`document.visibilityState`，重放只读日志快照。`beforePhase0` 先把本次捕获批次统一标记为当前 `deliveryBoundaryTick`，对整个批次整批完成全局 sequence 连续性与重复校验并写入原始 InputLogEntry；这一预检只记录每条输入的 sequence 校验结果，不得在此时预先分流规则命令，也不得预先产生 late、state 或 control 结果。预检完成后才严格按入口总 sequence 逐条处理；规则队列内允许因控制记录未入队而出现 sequence 间隙，但仍以 sequence 作为同 tick 唯一顺序。规则命令使用 `CommandEnvelope { targetTick, sequence, type, payload }`，其中 `targetTick` 是非负整数；首版规则命令保持有限：

- 预选材料、取消待投材料、投入一份材料；
- `SelectFireSource { fireSourceId }`：从原型配置允许的火种列表中选择并装备火种；
- 设置喷火开关、目标方向和火焰大小；
- 设置容器移动轴；
- 设置火焰推力开关；
- 请求正常结束。

规则命令队列按 `(targetTick ASC, sequence ASC)` 唯一排序。按总 sequence 处理到一条规则命令时，才依次使用批次预检得到的 sequence 结果、`targetTick < deliveryBoundaryTick` 和当时状态的许可矩阵做 `sequence invalid > late > state not allowed` 判断：全局 sequence 不连续或重复返回 `APP_COMMAND_SEQUENCE_INVALID`；sequence 合法但迟到则返回 `APP_COMMAND_LATE`，不得改投到当前或下一 tick；`targetTick === deliveryBoundaryTick` 可进入本 tick，未来 tick 则排队等待。不存在以“接受时 currentTick”或“phase 0 是否已截取”作第二套判断的路径，规则队列内由合法控制记录造成的间隙不算错误。同 tick 的离散命令逐条执行；喷火开关、方向、火焰大小和容器移动轴等 ordered/连续值按 sequence 应用，合法命令的最终值采用 last-write。非法命令产生稳定拒绝结果但不阻塞后续 sequence；成功 reset 建立的 cutover 除外，重放必须得到相同拒绝与丢弃列表。

应用控制使用 `ApplicationControlEnvelope { sequence, type, payload }`，类型仅含 Pause/Resume、窗口 blur/focus、页面 visibility、restart request/confirm/cancel，以及 failed/completed 页面的“再来一炉”；它们不进入规则命令队列，也不等待规则 tick 的 phase 0。application 以独立 application control channel 承载控制，但该通道不是先于规则命令整批排空的第二条时间线：按总 sequence 处理到控制时，非重入、串行的 control pump 必须在继续处理下一条输入前完成该控制，再回到同一批次的总 sequence 流。即使暂停或终态使规则 tick 停止，`beforePhase0` 和 control pump 也会运行。若输入在一个规则 tick 提交期间被捕获，只能等该完整 tick 结束后的下一个 `beforePhase0` 才交付；control pump 与 phase 0 不并发，也不得执行投药、溶解、运动、结算等任何规则推进。

failed/completed 不关闭输入边界门。终态下每次 `beforePhase0` 仍先完成整批 sequence 校验和原始日志写入，再按总 sequence 逐条处理：位于成功“再来一炉”之前的规则输入仍先判 `targetTick < deliveryBoundaryTick`，sequence 合法且非迟到则返回 `APP_COMMAND_NOT_ALLOWED`，不进入规则队列，也不启动 phase 0；处理到“再来一炉”时由 control pump 同步完成。若该控制成功 reset，则其后的同批输入走 reset cutover 的直接丢弃路径；若控制失败或不允许，则不建立 cutover，并继续处理后续 sequence。这样终态后的规则输入不会因 tick 停止而悬空，且结果由其相对成功 reset 的 sequence 位置唯一决定。

确定性重放只能在每条记录的 `beforePhase0(deliveryBoundaryTick)` 注入该边界的输入，先完成同一批次预检，再按总 sequence 经过同一逐条规则判断和 control pump；禁止预先把未来边界输入塞入队列，也禁止根据重放进度改写边界。于是 tick 7 提交期间捕获的 `targetTick: 7` 命令在首次运行和重放中都会于边界 8 得到 `APP_COMMAND_LATE`，tick 7 提交期间捕获的 Pause 也都只能在完整提交后、phase 0(8) 前生效。规则命令摘要、控制结果、拒绝和 `discardedByReset` 列表分别记录，但都必须由同一输入日志复现；同一批次成功 reset 的 cutover 位置也不得在重放时重算或后移。

应用层对火种流程提供以下 ReadModel 与命令语义：

- ReadModel 至少暴露可选火种稳定 ID 列表、`equippedFireSourceId: string | null`、已设置火焰大小、是否正在喷火和有效火焰大小；
- 新一炉的 `equippedFireSourceId` 初始为 `null`，即使配置中只有唯一火种也不得自动装备；
- 合法的 `SelectFireSource` 只装备火种，不点火、不喷火、不加热，也不改变已设置火焰大小；
- ready 或 extracting 中仅当 `equippedFireSourceId === null` 时允许首次装备；一旦已装备则禁止切换，返回 `APP_COMMAND_NOT_ALLOWED`；
- ready/extracting 中，只有已装备火种时才允许 `SetSpraying(true)`；未装备时必须返回稳定 `APP_COMMAND_NOT_ALLOWED`，且 `isSpraying` 保持 `false`。`SetSpraying(false)` 在这两个状态中始终允许用于清理且幂等，不要求已装备；方向、大小、推力开关和容器轴的原许可不变；
- 未装备火种时，喷火输入不能潜伏为将来的开启状态，也不能产生有效火流、升温、溶解、伤害或推力；随后合法 `SelectFireSource` 仍只装备，必须收到一条新的合法 `SetSpraying(true)` 才能点火；
- `ready` 同时涵盖未选择火种和已装备火种的待机阶段，无需为装备动作扩张状态机。

领域与模拟只产生具有业务含义的一次性事件，例如：

- 材料投入、珠子生成、护盾触发；
- 珠子受伤、接住、落空、烧毁；
- 警告等级变化；
- 争斗开始与结束；
- 可以结束；
- 萃取失败、萃取完成。

每帧位置变化不进入事件流，直接由只读模拟状态提供，避免制造海量事件。

### 5.4 最小状态机

~~~mermaid
stateDiagram-v2
    [*] --> ready
    ready --> extracting: 首次正式投药
    extracting --> failed: 药液流失率 > 70%
    extracting --> completed: canFinish 且玩家点击结束
    failed --> ready: 再来一炉
    completed --> ready: 再来一炉
~~~

- canFinish 由“所有已投入材料完全溶解且所有活动珠子完成结算”派生；
- “可以结束萃取”不是独立持久状态；
- 暂停是应用生命周期开关，不制造 readyPaused、extractingPaused 等组合状态；
- 焦黑、碎裂、聚拢和飞出属于失败表现序列，不进入领域状态机；
- 失败触发后领域立即禁用操作，表现层再播放 1～1.5 秒转化动画。

`canFinish` 的唯一公式为：`state === extracting && 投入实例数 > 0 && 所有已投入实例均完全溶解 && 活动珠子数 === 0`。这里的活动珠子包含已出生但要到下一 tick 才参与运动的新生珠，只排除已经接取、落空或烧毁的终态珠；UI 不缓存该值。

### 5.5 命令-状态许可矩阵与重开契约

领域状态之外只允许 application 持有 `restartConfirmation: closed | open` 与 `pauseReasons: Set<manual | blur | hidden | restartConfirmation>`；`paused` 只由 `pauseReasons.size > 0` 派生，它们都不扩张 domain 状态机。control pump 按控制顺序增删原因，Resume 或 cancel 不能清掉仍有效的其他暂停原因。所有“不允许”都由 application 返回稳定错误 `APP_COMMAND_NOT_ALLOWED`，禁用按钮不能代替命令侧校验。

| 命令 | ready | extracting | failed | completed |
| --- | --- | --- | --- | --- |
| 预选/取消待投材料、投入材料 | 允许；首次投入转 extracting | 允许 | 不允许 | 不允许 |
| `SelectFireSource` | 仅当 `equippedFireSourceId === null` 时允许首次装备；一旦已装备则禁止切换 | 仅当 equippedFireSourceId === null 时允许首次装备；一旦已装备则禁止切换 | 不允许 | 不允许 |
| `SetSpraying(true)` | 仅已装备火种时允许；未装备稳定拒绝且保持 false | 同左 | 不允许 | 不允许 |
| `SetSpraying(false)` | 始终允许、幂等清理且不要求装备 | 同左 | 进入终态时已被强制清理；规则命令不再推进 | 同左 |
| 方向、大小、推力开关、容器轴 | 允许 | 允许 | 不允许 | 不允许 |
| 暂停/恢复、失焦/可见性 | application 处理 | application 处理 | 只允许清理输入，不推进模拟 | 只允许清理输入，不推进模拟 |
| 请求正常结束 | 不允许 | 仅 `canFinish` 为真时允许 | 不允许 | 不允许 |
| 请求重开 | 打开二次确认 | 打开二次确认 | 直接执行“再来一炉” | 直接执行“再来一炉” |
| 确认/取消重开 | 仅确认弹板打开时由 application 处理 | 同左 | 不适用 | 不适用 |

ready/extracting 的 restart request 由 control pump 打开确认弹板、强制停火、清空累加器并暂停规则 tick；cancel 只关闭弹板并移除 `restartConfirmation` 暂停原因，domain、simulation、clock/tick、RNG 和规则命令队列均不改变。confirm 以及 failed/completed 的“再来一炉”都由 control pump 调用同一个原子 `resetSession`。成功 reset 先停止推进并屏蔽输入，并以该控制为旧会话最后一条 applied input 建立 reset cutover：把规则队列中所有已经入队但尚未执行的命令，包括 targetTick === deliveryBoundaryTick 与未来 tick，按 `(targetTick ASC, sequence ASC)` 稳定顺序逐条记为 `discardedByReset` 后清空，不得冒充 `APP_COMMAND_LATE` 或 `APP_COMMAND_NOT_ALLOWED`；终态 phase 10 的正常抽干仍是进入终态时的契约，但不能据此跳过本边界 cutover 对尚无结果命令的兜底归档。在不可观察的事务中归档而非抹除已有命令结果与拒绝结果，再清空事件缓冲、clock/tick/累加器和会话 RNG，回收材料/珠子/互动实体占用项与全部 Phaser Sprite，注销会话级监听器和计时器，重置装备火种、喷火/余焰/推力、方向、火焰大小、炉温、容器、库存/预选、投入实例、流程状态、体积台账、警告/失败/完成结果和 restartConfirmation；再按 prototype 与 seed 初始化新一炉、重建一次监听器。被拒绝、不允许或事务未成功的 confirm/“再来一炉”不建立 cutover，并继续处理后续 sequence。

reset 的暂停与日志处理也属于同一事务：关闭 `restartConfirmation` 并移除同名原因，清除旧会话的 `manual` 原因；使用触发 reset 的旧会话控制所记录的 `lifecycleSnapshot` 重新采样语义，按 `!hasFocus` 决定是否保留 `blur`、按 `visibilityState !== 'visible'` 决定是否保留 `hidden`，最后才由新 `pauseReasons` 派生 `paused` 并一次性发布 ready ReadModel。实现在线运行时的快照值来自当前 `document.hasFocus()` 与 `document.visibilityState`，确定性重放使用日志值；后续 focus/visibility 控制同样携带完整快照并同步这两个原因。因此可见且聚焦时 confirm 后的新 ready 可推进，后台 confirm 后仍暂停，收到记录为 visible 且 focused 的生命周期控制后才恢复。

触发 reset 的 confirm/“再来一炉”控制属于旧 `sessionId`；事务归档旧 session 的完整原始输入日志、最后已捕获 sequence、最后 applied sequence 和结果摘要，该控制是旧会话最后一条已应用输入。原始输入日志可以保留 cutover 后的条目，但同批所有更大 sequence 输入不再执行 late、state 或 control 判断、不进入新 session，直接按 sequence 记录 `discardedByReset`，随后结束该旧 session 的本次边界处理；已排队规则命令则按上述稳定顺序归档。reset cutover 对后续错误优先级具有因果优先权，因此后续输入即使自身会迟到、状态不允许或也是控制，也只能得到 `discardedByReset`。reset 完成并解除输入屏蔽后，创建新的 `sessionId`，把待执行 tick、输入 sequence 和日志分别重新初始化为 0、1 和空；新会话只接收 reset 完成后未来捕获的新输入，不能消费旧批次剩余项。对象池和 Sprite 池只要求 occupied 回零并复用容量，不要求已达到的高水位收缩。任何中间状态不得被 UI/game 观察；reset 完成前 control pump 不处理下一条控制，旧会话的该次边界处理结束前 phase 0 也不能开始。

## 6. 配置与素材管线

### 6.1 配置处理流程

~~~text
原始 JSON
  → JSON Schema 结构校验
  → 跨文件稳定 ID 与引用校验
  → 数值范围、单位和枚举校验
  → 图片尺寸、颜色、轮廓包含关系校验
  → 合并公共默认值
  → 解析为只读标准化配置
  → application/domain/simulation 使用
~~~

实现要求：

- JSON Schema 是原始配置格式的唯一契约，网页端用 Ajv 校验；
- 每份配置都带 schemaVersion；
- 未知的更高版本明确拒绝，不猜测兼容；
- 每次完整加载计算下述 `simulationContentFingerprint`，用于 bug 复现和测试向量；
- 配置错误同时提供稳定错误码、文件路径、字段路径和明确中文说明；
- 开发环境在错误界面展示问题，生产构建拒绝开始模拟，不静默采用错误值；
- 标准化配置完成后只读，规则层不再读取原始 JSON；
- 路径与表现字段在 config/game 边界消化，domain 与 simulation 只看逻辑 ID 和规则数据。
- Schema 明确限制 materials 只保存药性、功效线索、反应特性、风险四类固有标签，prototype 库存批次的状态字段只保存保存状态、生长来源和年份；禁止在材料定义中写入或重复固化派生状态标签；
- 跨文件校验确认 prototype 的材料与可选火种 ID、materials 的四类固有标签 ID、状态批次值及 tags.json 的规则引用全部存在且类别匹配；
- 标准化阶段组合材料固有标签与库存批次数据，按 tags.json 的集中规则派生第五类状态标签，并输出只读的五类标签视图。

`simulationContentFingerprint` 使用以下唯一算法，脚本、运行时和未来 Unity 工具共享 golden fixture：

1. 枚举会影响 domain/simulation 的规则 JSON，以 UTF-8 规范化相对路径排序后解析；发现顺序只用于消除文件系统差异。每份规则必须提供由 Schema 类别和稳定 ID 组成的唯一逻辑键，最终哈希记录按逻辑键排序，相对文件名和目录名本身不进入哈希；因此只重命名/移动文件且不改变逻辑内容不会误改指纹，重复逻辑键则拒绝加载。
2. 去掉 Schema 明示的纯表现字段，把成分图路径引用解析成对应材料稳定 ID 的规则资源；其余规则值按 RFC 8785/JCS 生成 canonical JSON UTF-8 字节。对象键书写顺序、空白和换行不影响结果，数组顺序仍按 Schema 语义处理。
3. 对每个材料按稳定 ID 排序，追加已解码的 64×64 成分图规则字节：固定写入无符号大端 `width=64`、`height=64`，再写入从左上到右下、逐行、每像素 `R,G,B,A` 的 16384 个原始字节；PNG 压缩方式和元数据不进入指纹，像素改变必须改变指纹。
4. 所有记录使用带类型和字节长度的二进制 framing 后求 SHA-256，小写十六进制即 `simulationContentFingerprint`。材料外观、纹理、音频、CSS 等纯表现资产不进入该指纹，可另算 `buildAssetHash`；表现路径只在纯表现字段中重命名不改 simulation 指纹。

测试必须证明：JSON 键序/空白变化和规则文件纯重命名不改指纹；等价重编码但解码 RGBA 相同的成分 PNG 不改指纹；任一成分像素、规则值、稳定 ID 或数组语义顺序变化必改指纹；纯表现资产变化只改可选的 build asset hash。

### 6.2 参数归属

| 配置 | 主要内容 |
| --- | --- |
| prototype.json | 1600×900 场景、测试库存；每个库存批次的状态字段只含保存状态、生长来源、年份；可选火种稳定 ID 列表、火焰大小初始值、试玩开关、布局和调试入口 |
| parameters.json | 模拟频率、时间、随机、全局 `standardPearlVolume`、`slagUnitVolume`、流场、溶解、流失、警告、失败转化、药渣换算、界面通用参数 |
| tags.json | 五类标签定义与状态派生规则的单一来源；根据批次保存状态、生长来源和年份派生第五类状态标签 |
| materials/ | 8 种材料的稳定 ID、中文名、每份 `targetPearlCount`、药性/功效线索/反应特性/风险四类固有标签、外观图、成分图、颜色、显示覆盖项 |
| fire-sources.json | 火种温度曲线、升降温、火源注入、角度、宽度和推力 |
| pearl-types.json | 三类珠子的运动、护盾、灼烧、受力、轮廓、纹理、动画和音效组 |

公共默认值只能定义一次。材料配置只覆盖差异，不复制一整套相同参数；派生状态标签只存在于标准化结果，不回写 prototype 或 materials 原始配置。

本项目统一使用无量纲但命名明确的“逻辑体积单位”。`parameters.json` 全局 `standardPearlVolume` 默认 `1`，`slagUnitVolume` 默认 `100 × standardPearlVolume`；每种材料的 `targetPearlCount` 默认 `300`，允许材料定义按试玩目标覆盖。单份标准材料逻辑总体积固定为 `targetPearlCount × global standardPearlVolume`。64×64 成分图中三种合法非空像素只提供类型与分布权重：每个非空像素权重相同，各类型像素数归一到该材料逻辑总体积；不得再配置三类固定数量、固定体积或各材料自己的完整珠体积。所有材料、所有类型的完整珠均使用同一份全局 `standardPearlVolume`，只有不足一颗的尾量珠按体积比缩放。

Schema 与标准化器明确所有权和范围：`standardPearlVolume` 是 parameters 全局必为有限正数、默认 1，材料不得覆盖；`slagUnitVolume` 是 parameters 全局有限正数、默认前者的 100 倍；`targetPearlCount` 仅由材料定义覆盖，必须是 `1..100000` 的整数、默认 300；非空成分像素数必须大于 0。原始配置省略项由标准化阶段补默认值，运行时只读取标准化后的显式值。

## 7. 核心领域与模拟设计

### 7.1 固定 tick

- requestAnimationFrame 只驱动渲染和累加真实时间；
- application 使用固定 1/30 秒步长推进规则与模拟；
- 单帧只允许有限补步，超过上限的积压记录为调试告警，不能造成恢复后长时间追帧；
- 页面后台、失焦、弹板打开或手动暂停时清空累加器并强制停火；
- 恢复后必须由玩家重新按下左键才会喷火；
- 输入命令记录目标 tick，保证同一命令序列可重放；
- 暂停、恢复、可见性和重开走第 5.3 节 control pump；规则 tick 停止时控制仍可处理，但不得借控制泵推进规则；
- 如高速珠子出现穿透，优先增加扫掠碰撞或局部子步，不擅自提高全局规则频率。

每个活动 tick 之前必须先完成第 5.3 节唯一的 `beforePhase0(deliveryBoundaryTick)` 门：接收并标记本边界输入，先对捕获批次整批完成全局 sequence 校验和原始日志写入，再严格按入口总 sequence 逐条处理。遇规则输入时才按 `sequence invalid > late > state not allowed` 判断并入队或拒绝；遇控制时由非重入 control pump 在下一条输入前处理完成。failed/completed 时，成功“再来一炉”之前的规则仍依次得到 late 或 `APP_COMMAND_NOT_ALLOWED`，成功控制之后的同批输入则由 reset cutover 直接记为 `discardedByReset`。若未建立 cutover，再由 `pauseReasons`/终态状态决定是否开始 phase 0；若建立 cutover，则结束旧会话本次边界处理，不用新会话在同一边界启动 phase 0。获准推进时才令 `currentTick = deliveryBoundaryTick` 并进入 phase 0。该门不是规则 phase，不推进时钟、RNG、domain 或 simulation；phase 0～10 一旦开始，直到 phase 10 原子提交完毕都不再接收浏览器输入。每个获准活动 tick 只允许按下表推进；该表是唯一权威 tick phase，任何优化不得跨 phase 改写可观察语义：

| phase | 顺序与唯一职责 |
| --- | --- |
| 0 命令 | `beforePhase0` 已按总 sequence 处理完捕获批次、所有已遇控制均已完成且确认可推进后，截取 `targetTick === currentTick` 的规则命令批次并按 sequence 执行；处理 last-write 和非法状态/载荷拒绝并形成确定性命令结果。迟到命令已在边界门拒绝；应用控制、输入交付和原子 reset 均不在本 phase 执行。 |
| 1 投药 | 按命令顺序扣库存、创建材料实例并暂存新增理论体积与继承损失；首次合法投药使 ready 转 extracting。 |
| 2 障碍 | 从本 tick 投入后的材料格与 tick 开始前已有的活动珠重建/更新障碍；新生珠尚不存在。 |
| 3 流场 | 以 phase 2 的只读障碍求本 tick 唯一 FireFlowField。 |
| 4 溶解与产珠 | 采样 phase 3 流场，扣材料格并把达到完整体积或最终尾量的珠写入 `newborn` 队列；新生珠计入未结算活动数，但下一 tick 才进入运动、障碍、灼烧、推力、碰撞和互动。 |
| 5 既有珠更新 | 只更新 tick 开始时已 active 的珠，固定子序为运动积分 → 灼烧/护盾/伤害 → 火焰推力 → 炉壁与材料碰撞 → 空间网格互动；只写 simulation 暂存变化。 |
| 6 实体终态 | 判定接取、落空、烧毁并确保每实体至多一个终态；同 tick 冲突优先级固定为 `burned > caught > missed`，终态实体立即退出互动和后续 eligible 集合。 |
| 7 自然流失 | 按第 7.7 节从 phase 6 后仍 eligible 的材料药液格和 active 药液珠计算并分摊自然流失；不作用于 newborn、已接取或非药液体积。 |
| 8 原子账本 | application 汇总投药、溶解、出生、体积变化、实体终态、自然/继承流失为一个 `SimulationDelta`，先验证守恒与非负，再让 domain 一次提交库存、流程与台账；失败不得留下半笔。simulation 实体和 domain 台账禁止互相直接写。 |
| 9 阈值与状态 | 由提交后的账本派生流失率、两级警告、`canFinish` 与终态。若同 tick 同时满足会话终态，优先级固定为 `failed > completed > extracting/ready`；完成请求只能在未失败且提交后的 canFinish 为真时生效。 |
| 10 提交视图 | 若 phase 9 刚进入 failed/completed，先把规则队列内全部尚未执行的命令按 `(targetTick ASC, sequence ASC)` 抽干，保留其既有 `InputLogEntry` 并逐条记录 `APP_COMMAND_NOT_ALLOWED` 拒绝结果，使队列为空；再按稳定事件类型、实体 ID 和产生序号提交 DomainEvent，激活 newborn 供下一 tick 使用，然后只发布一次 ReadModel。拒绝结果与终态一并原子提交，事件订阅者不能反写本 tick。 |

`SimulationDelta` 至少携带 tick、各材料/类型的溶解与出生体积、每颗珠体积变化、接取/落空/烧毁终态、自然流失、继承损失和对应稳定实体 ID。phase 8 在内存临时副本上完成全部校验后才交换引用或提交事务；任何一项失败返回稳定 invariant 错误并保持 tick 前的 domain 台账，不能逐字段补偿。确定性向量必须包含同 tick 多次火焰大小/方向 last-write、投药后当 tick 进入障碍与溶解、新生珠不在当 tick 受火/接取，以及同一既有珠同时满足烧毁与接取时只记烧毁的 RED→GREEN 用例；还必须包含 tick 7 phase 0 截取后捕获的 `targetTick: 7, sequence: 10` 在 `deliveryBoundaryTick: 8` 首次执行与重放均迟到，以及 tick 7 提交期间捕获的 Pause 只能在完整提交后生效。另一个终态向量在 extracting tick `t` 预排 `targetTick: t+1` 的 future 规则命令，让 phase 9 因流失率超过 70% 进入 failed，再在 `beforePhase0(t+1)` 交付一条同边界规则命令；前者由 phase 10 抽干、后者由终态边界门直接拒绝，两条均为 `APP_COMMAND_NOT_ALLOWED`，按 sequence 形成相同顺序，队列为空，控制通道仍能执行“再来一炉”。另设三组批内 cutover 向量：`reset-cutover-active-batch` 从 extracting、确认弹板已打开、boundary 8 注入 `[s10 ConfirmRestart、s11 targetTick: 8]`，期望 s10 成功 applied、s11 为 `discardedByReset`；`reset-cutover-terminal-first` 从 failed、boundary 8 注入 `[s20 Again、s21 targetTick: 7、s22 targetTick: 8]`，期望 s20 成功 applied，s21/s22 均为 `discardedByReset` 而不是 late/not allowed；`reset-cutover-terminal-prefix` 注入 `[s19 targetTick: 7、s20 Again、s21]`，期望 s19 为 `APP_COMMAND_LATE`、s20 成功 applied、s21 为 `discardedByReset`。三组向量的首次运行与重放得到相同结果、日志和顺序。

### 7.2 二维火流

首版不追求完整流体力学，只实现满足玩法的低分辨率定向火流：

1. 火源按配置的位置、方向和宽度向网格注入流向与可达量；
2. 药材未溶解格写入完全障碍；
3. 珠子按圆形覆盖面积写入 0～1 部分障碍，同格累加并封顶为 1；
4. 火流遇障碍后依据障碍梯度向两侧分流，在障碍后按配置逐渐汇合；
5. 当前不做强度衰减；只要火流可达，正面与绕流位置使用同一灼烧强度；
6. 输出统一的 flowX、flowY、reachable/intensity 网格；
7. 渲染、溶解、伤害和推力只能采样这一输出。

具体求解器必须隐藏在 FireFlowField 接口后。M1 先用可视化技术场景验证“阻挡、两侧绕行、缺口恢复、珠群增强阻挡、绕后汇合”五个行为；若简化求解器无法通过，再替换内部算法，不影响上层模块。

开发模式提供流场覆盖层，可切换显示障碍值、方向、可达区和每步耗时。

### 7.3 材料堆与局部溶解

每份投入材料是独立实例，包含：

- 稳定材料 ID、批次状态和投入序号；
- 固定世界位置、旋转、缩放和层级；
- 64×64 成分类型；
- 每格剩余体积；
- 三类待产珠体积累加器；
- 显示遮罩所需的只读剩余比例。

实现规则：

- 先投入的实例在下层，后投入的实例在上层；
- 位置偏移与旋转来自配置范围和确定性布局随机流；
- 材料不坍塌、不重新排列；
- 火带按 `frontLaneWidthCells` 与材料格投影宽度离散成确定性前沿通道，每条通道仅取最靠近火源的剩余格；
- 单份材料只要至少有一格受火，本 tick 总溶解量固定；
- 同一时刻只续烧显式 `pendingFireCellIndex` 指向的未完成格；该格烧完后再按通道相对深度、横向距离和稳定 cell index 选下一格，自然损耗 partial 不参与 fire-front 推断；
- 前沿通道少时形成深缺口，通道多时形成宽浅剥离；
- 多份材料分别并行计算，不共享一份总速率；
- 外观遮罩从同一份剩余格数据生成，不能另建视觉进度。

单份材料总逻辑体积按第 6.2 节由 `targetPearlCount × global standardPearlVolume` 得到，再按成分图非空像素权重分到每格。每类实际溶解体积累计达到全局 `standardPearlVolume` 时，在最近的实际溶解位置生成对应完整珠；材料完全溶解时，只将扣除自然/继承损失后的不足一颗尾量生成等比例缩小珠子。成分图不推导各材料不同的标准珠体积。

### 7.4 精灵珠数据与运动

概念上的 `PearlEntity` 最小契约如下；实现可为结构化数组，但字段语义不得缺失：

~~~ts
type PearlEntity = {
  pearlId: PearlId;
  sourceMaterialDefinitionId: MaterialDefinitionId;
  sourceMaterialInstanceId: MaterialInstanceId;
  type: "medicinalLiquid" | "slag" | "impurity";
  tags: readonly TagId[];
  configRef: Readonly<{ pearlTypeId: PearlTypeId; interactionProfileIds: readonly InteractionProfileId[] }>;
  currentVolume: number;
  radius: number;
  position: Readonly<{ x: number; y: number }>;
  velocity: Readonly<{ x: number; y: number }>;
  state: "newborn" | "active" | "caught" | "missed" | "burned";
  shield: Readonly<{ active: boolean; remainingTicks: number }>;
  damage: Readonly<{ accumulated: number; protectionTicks: number }>;
  interactionTimers: Readonly<Record<string, number>>;
  safeZone: Readonly<{ entered: boolean; enteredTick: number | null }>;
};
~~~

`sourceMaterialDefinitionId` 和 `sourceMaterialInstanceId` 都必须保留，分别用于配置/标签追溯和单份材料守恒；tags 是出生时从该实例派生的稳定 ID 只读快照，`configRef` 只保存标准化配置稳定 ID，不复制可变配置。`currentVolume` 是珠体积事实，radius 只能由它和全局标准珠体积公式派生；position、velocity、state、shield、damage、interactionTimers、safeZone 均由 simulation 单写。application/game/ui 只能获得按 tick 生成的深只读快照或不可写视图，不得持有可变数组引用。

为满足 2400 颗活动珠性能目标：

- simulation 使用数据池或结构化数组保存珠子数据；
- game 使用独立的 Phaser Sprite 池；
- 不为每颗珠子创建完整刚体、独立计时器或独立音轨；
- 模拟对象 ID 与显示对象 ID 显式映射；
- 接取后的珠子退出复杂模拟，切换为轻量展示状态；
- 重开时两个池分别回收，不能依赖场景销毁侥幸清理。

珠子规则：

- 从实际溶解位置生成，使用可配置初速度、重力、漂移和最大速度；
- 与丹炉边界和材料剩余遮罩碰撞；
- 药材缺口形成后立即允许通过；
- 珠子之间不做全量刚体碰撞；
- 灼烧区内参与挡火、护盾、伤害和推力；
- 越过火源高度进入安全接取区后，永久退出挡火、伤害和推力，但仍可触发配置互动；
- 剩余体积同步决定显示大小、碰撞半径、障碍覆盖和接取贡献；
- 火焰推力关闭后不再施加新力，但保留既有速度。

### 7.5 空间网格与互动

- 空间网格只索引需要邻近查询的活动珠子；
- 每颗珠子只查询相邻格，不遍历全场；
- 首版只实现“争斗”策略；
- interactions.json 指定双方材料或标签、距离、持续时间、弹开力量、冷却和表现；
- 赤须参与寒髓晶是首个配置实例，代码不得识别这两个中文名或稳定 ID；
- 同一珠子同一时间最多参与一次互动；
- 安全区仍可开始或继续争斗；
- 接住、落空或烧毁后立即退出互动和索引。

### 7.6 炉温

炉温是独立领域值：

> 有效火焰大小 = equippedFireSourceId 不为空且正在喷火 ? 已设置火焰大小 : 0  
> 目标炉温 = 基础炉温 +（最高炉温 - 基础炉温）× 温度曲线（有效火焰大小 ÷ 100）

- 首版火种使用线性曲线；
- 未装备火种时有效火焰大小恒为 0，不能产生有效火流或加热；选择火种只更新装备状态；
- 实际炉温按配置升温或降温；
- UI 只显示黄到红的竖向条，不显示数字；
- 当前炉温不得影响材料溶解或自然流失；
- 炉温测试必须专门证明“改温度不改当前萃取结算”。

### 7.7 体积台账

领域层维护统一账本，至少区分：

- 全部已投入材料的理论药液体积；
- 未溶解材料中仍暴露的药液体积；
- 活动药液珠剩余体积；
- 已接取有效药液体积；
- 已烧掉药液体积；
- 已落空药液体积；
- 已自然蒸发药液体积；
- 追加材料按既有流失率继承的药液损失体积 `inheritedLossVolume`；
- 已接取药渣污染体积；
- 已接取杂质污染体积；
- 炉底药渣池中三类落空对象的剩余体积；
- 失败瞬间仍存在的实体总体积。

药液流失率统一计算为：

> 若 `理论药液总体积 === 0`，则 `流失率 = 0`；否则  
> `流失率 = clamp((自然蒸发药液体积 + inheritedLossVolume + 实际烧掉药液体积 + 落空药液剩余体积) / 理论药液总体积, 0, 1)`

自然流失统一使用逻辑体积单位。phase 7 的 eligible 集合严格等于“仍未溶解的药液成分格 + phase 6 后仍为 active 的药液珠”；排除 newborn、已接取/落空/烧毁珠、药渣、杂质、已接取展示物和待产累加器。设其当前总体积为 `eligibleVolume`，配置每分钟比例为 `ratePerMinute`，固定步长秒数为 `dt`，则每 tick：

> `naturalLossThisTick = clamp(eligibleVolume × ratePerMinute × dt / 60, 0, eligibleVolume)`

分摊项使用稳定键 `cell:<materialInstanceId>:<pixelIndex>` 或 `pearl:<pearlId>` 升序排列，按分摊前体积比例计算。除最后一个仍有容量的项外依次写入比例份额，最后一项承接 `naturalLossThisTick - 已分配和` 的浮点尾差；若 clamp 造成容量不足则按稳定键逆序回填，保证分摊和在约定 epsilon 内等于本 tick 损失且不产生负数。材料格份额同步扣其 current/remaining/spawnable volume，并在同 tick 重建外观遮罩与材料碰撞；珠份额同步扣 `currentVolume`，重算 radius、碰撞和障碍贡献，归零则在该 phase 转为 burned 并进入同一 `SimulationDelta`。待产累加器只累计实际溶解量：自然损失不得进入累加器，材料的可产余额和最终尾量上限必须同步扣除该损失，禁止完全溶解时把已流失体积补产成尾量珠。

中途追加理论药液体积 V 时：

1. 读取追加前流失率 R；
2. 计算该新材料成分图中的药液理论体积 V；理论药液分母增加 V；
3. `inheritedLossVolume` 原子增加 `V × R`，并按新材料药液格的稳定 pixelIndex 与原始可生成体积比例，从这些格的 current/remaining/spawnable volume 扣除同样的 `V × R`；药渣和杂质格不扣；
4. 上述分母、继承损失、材料格、遮罩/碰撞和可产尾量在 phase 8 同一个 `SimulationDelta` 提交，任一校验失败全部不写；
5. 提交前后流失率保持 R，实际可生成的新药液体积为 `V × (1 - R)`。

账本必须满足以下不变量：

- 所有数量有限且非负；
- 比例始终在 0～1；
- 同一体积不能同时进入两个结算去向；
- 接取后的药液不再自然流失；
- 药渣与杂质不进入药液流失分子；
- 完全烧毁珠子不进入炉底药渣池；
- 部分烧毁后落空只把剩余体积进入炉底药渣池；
- 自然蒸发的体积不参与失败药渣数量。
- 药液理论分母必须能解释为未溶解格、待产累加、活动珠、接取、烧毁、落空、自然损失和 inherited loss 的互斥总和。

落空药液只有一个物理终态和去向：其剩余体积进入炉底药渣池；台账与流失指标对“落空药液剩余体积”的引用只是引用同一份体积，不是第二次实体结算或第二份体积，守恒总和只在“落空”项计一次。

### 7.8 警告、失败和完成

- 流失率达到 50% 时进入一级警告；
- 流失率达到 65% 时进入二级警告；
- 恰好 70% 不失败，只有超过 70% 才立即失败；
- 警告和失败阈值全部配置化，但比较语义由代码固定并测试；
- 失败后立即停火、停计时、禁用输入，领域状态进入 failed；
- 表现层播放焦黑、碎裂、聚拢和飞出；
- 失败药渣数量按失败瞬间剩余实体体积除以标准药渣体积向下取整；只要仍有内容，最低一份；
- 正常完成不会自动触发；canFinish 为真后仍等待玩家点击；
- 点击完成后停止模拟，容器中的珠子保留轻量展示，并显示临时完成弹板。

## 8. Phaser、DOM 与输入边界

### 8.1 场景与缩放

- Phaser 使用 1600×900 逻辑分辨率；
- 浏览器中等比缩放、居中，不拉伸；
- HTML UI 与 Canvas 共享同一外层坐标容器；
- 布局和边距从配置读取；
- 至少对 1920×1080、1366×768 做自动截图与人工检查。

### 8.2 输入路由

输入优先级按以下顺序执行：

1. 弹板与 HTML 控件；
2. 背包、待投材料和 Tips；
3. Phaser 游戏空白操作区。

必须保证：

- 初始界面显示火种选择；即使只有唯一选项也等待玩家选择，点击选项只发送 `SelectFireSource`；
- UI 从 ReadModel 渲染可选项和 `equippedFireSourceId`，不得自行缓存或推断装备状态；
- 未装备火种时，空白区按住左键也不产生有效火流或加热；选择后仍须重新按下左键才喷火；
- UI 区域按下左键不会喷火；
- UI 区域移动鼠标或滚轮不改变火焰；
- 背包左键预选，待投材料左键投入、右键取消；
- 游戏区禁用浏览器默认右键菜单；
- 空白区按住左键喷火；
- window 级 pointerup、blur 和 visibilitychange 都强制停火；
- 鼠标目标方向被限制在配置的朝上扇形；
- 滚轮和滑动条写入同一个火焰大小值并双向同步；
- A、D 同时按下时容器减速停止；
- 相反方向切换时先减速再反向；
- 恢复焦点后不自动恢复喷火。

### 8.3 表现层

- 药材采用手绘平面、清晰深色描边、无阴影；
- 丹炉使用暗青铜、暗红和深褐；
- 火焰使用黄、橙、红，绕流、分叉、遮蔽和汇合必须可读；
- 正常珠与炉体对火焰的最终画面遮挡按表现几何在热场分辨率生成复用遮罩，并允许配置半径缩放和柔边；不得把粗流场格整格清空成方洞。性能基准的小圆代理仍保留流场网格路径，避免视觉验收参数污染性能门禁；
- 三类珠子同时用轮廓、纹理、运动和受伤表现区分；
- 主题色、字号、描边和纹理由集中主题配置或 CSS 变量管理；
- 护盾、蒸汽、受伤、警告、失败和争斗表现订阅语义事件；
- 声音通过时间窗合并，禁止每颗珠子同时创建独立音轨；
- 纯余焰可以继续显示，但不能继续产生溶解、伤害或推力。

### 9.3 确定性测试向量

test-vectors/ 保存语言无关的 JSON：

- schemaVersion；
- 配置集合版本或哈希；
- 初始 seed；
- 按 sessionId 和全局 sequence 排序的 `InputLogEntry`；每条规则命令与应用控制都显式带 `deliveryBoundaryTick`，规则命令的 envelope 另带 targetTick，需要生命周期事实的控制 payload 带 `lifecycleSnapshot`；不得保存或推导模糊的“接受时 currentTick”；
- 关键 tick 的规范化状态摘要；
- 最终领域事件摘要与结算。

这不是玩家存档或丹方功能，只用于复现 bug、回归和未来 Unity 对照。重放器只允许在对应 `beforePhase0(deliveryBoundaryTick)` 注入记录；fixture 至少包含 `targetTick: 7, deliveryBoundaryTick: 8` 得到 `APP_COMMAND_LATE`、tick 7 完整提交后才应用 Pause、终态前 future 命令加终态后同边界命令得到两条顺序一致的 `APP_COMMAND_NOT_ALLOWED` 且队列为空，以及 reset 前后两个 session 各自独立 tick/sequence 的 RED→GREEN 向量。还必须保存 `reset-cutover-active-batch`、`reset-cutover-terminal-first`、`reset-cutover-terminal-prefix` 三组向量，分别断言“confirm 后同批当前 tick 规则丢弃”“Again 后同批 late/当前 tick 规则都因 cutover 丢弃”“Again 前 late、Again 后丢弃”；首次运行和重放必须得到相同输入日志、applied/拒绝/`discardedByReset` 结果及顺序，并证明控制通道仍可“再来一炉”。状态摘要不包含 Phaser 对象、资源 URL、内存地址或纯视觉字段。

这里的“配置集合版本或哈希”必须使用第 6.1 节定义的 `simulationContentFingerprint`。固定 fixture 同时保存 canonical JSON/framing 的中间十六进制摘要和最终 SHA-256，供 Web 与 Unity 独立实现对照；测试包含键序、文件重命名、PNG 重编码不变，以及规则值/成分 RGBA 改变必变的正反例。

- 先投入材料进入 extracting，再首次选择火种并重新按住左键，能够产生有效火流；首次装备后再次选择其他火种被稳定拒绝；

- 空白区喷火，任意位置松开立即停火；
- 火焰方向扇形限制；
- 滚轮与滑动条同步；
- HTML 控件不会误点火；
- A、D 移动容器；
- 右键菜单边界；

### 9.5 性能测试

性能场景通过测试配置生成，不在生产规则中写死珠子数量。900/2400 场景使用独立的小圆代理测量最坏负载，不代表玩家正常看到的珠子尺寸与构图；玩家可视 probe 使用半径 32px 的圆形流场碰撞代理、64px 高的水滴珠表现和匹配水滴主体宽度的精确圆形火焰遮罩，数量较低且占位密度受限。性能小圆与玩家可视珠不得互相复用表现或遮挡参数。

M1 先执行以下数值门禁，它是继续实现的技术预算，不替代 M6 的完整性能、回归和泄漏验收：

1. 使用生产构建、前台无最小化的固定 Chromium 版本，关闭 DevTools 与无关标签页；Canvas 逻辑/输出均为 1600×900、DPR=1、浏览器缩放 100%。首份报告把 CPU、GPU、内存、OS、浏览器精确版本登记为固定基准机；更换任一项只能产生不可混用的新基线。
2. 900 和 2400 两个配置场景各自执行 10 s 预热 + 60 s 采样。按 `performance.now()` 记录每次 `FireFlowField.update` 的 wall time：900 场 p95 ≤ 6 ms、max ≤ 10 ms；2400 场 p95 ≤ 8 ms、max ≤ 12 ms。
3. 固定步不得丢 tick，`droppedTickCount` 必须为 0。60 s 采样期总推进数与 `60 × 30 = 1800` 的误差 ≤ 1；连续、互不重叠的完整 1 s 窗口因计时边界允许 29～31 tick，但不得以窗口容差掩盖总量或 dropped tick。
4. 同一完整 1 s 窗口以提交给 requestAnimationFrame 的有效渲染帧数计 FPS：900 场每个窗口 ≥ 59 FPS，2400 场每个窗口 ≥ 45 FPS；同时保留逐帧帧时间用于诊断，不用瞬时单帧倒数代替窗口口径。
5. 记录活动珠数、互动数、流场调用次数和所有门限原始样本，检查没有自动删珠、合并真实珠、跳过规则或自动降质。任一数值失败即停在 M1，只允许优化/替换 FireFlowField 内部算法或数据布局并重跑门禁，不得带着失败进入 M2。

M6 在同一固定基准机、构建和采样口径重跑两场，并执行可判定的 10 炉生命周期协议：先用 900 珠完整跑 3 炉预热对象池/JIT，重开 ready 后通过 CDP `HeapProfiler.collectGarbage`（若该 Chromium 不支持，则用启动参数暴露的 `gc()`，报告只能选择并固定一种方式）连续触发两次 GC，等待 500 ms 后记录 ready 基线；随后连续跑完并重开 10 炉，每次都在相同 ready 时点用同样两次 GC 与等待时间记录 post-GC heap、监听器、活动对象、池 occupied/capacity 和 Sprite occupied/capacity。

令 `heap1..heap10` 为 10 炉各自在相同 ready 时点记录的 post-GC heap。绝对门禁保持为：每炉相对 ready 基线的增量均须 ≤ `max(5 MiB, 基线 heap × 5%)`。增长趋势门禁定义 `trendTolerance = max(1 MiB, 基线 heap × 1%)`，并同时要求 `mean(heap6..heap10) - mean(heap1..heap5) <= trendTolerance` 与 `heap10 - heap1 <= trendTolerance`；任一条件失败即判泄漏门禁失败。application/game/ui 的会话监听器计数、活动材料/珠子/互动/计时器数和两个池 occupied 必须精确回到 ready 基线。对象池与 Sprite 池 capacity 不强求收缩，只要求在预热达到 900 场高水位后 10 炉内不再增长。任何自动重试或手工 GC 次数变化均使报告无效。

性能证据至少保存 production commit/build 标识、`simulationContentFingerprint`、基准机/浏览器信息、场景配置、逐帧/逐流场调用/逐秒窗口 CSV 或 JSON、dropped tick 计数、10 炉 post-GC heap 原始表、监听器和池计数，以及失败时的 trace/snapshot 路径。报告汇总平均值、中位数、p95、max 和逐秒最低 FPS，不只报告最好结果；内存部分还必须原样列出基线、每炉 heap/相对增量、absolute tolerance、trendTolerance、前后五炉均值及其差、heap10-heap1 和每项 PASS/FAIL，不得只给最终结论。不同硬件 CI 只做趋势参考，不能冒充固定基准机硬门禁。

### 9.6 覆盖率使用原则

- domain 与 config 以高分支覆盖为目标，建议不低于 90%；
- simulation 建议不低于 80%，同时必须有不变量和性能场景；
- game 与视觉表现不追逐行覆盖率，以 E2E 和人工视听验收为主；
- 覆盖率只用于发现漏测，不能替代关键场景证据。

## 12. 风险与应对

| 风险 | 早期信号 | 应对与决策门 |
| --- | --- | --- |
| 简化火流无法形成可信绕流 | 火焰穿物、背后立即受火、绕后不汇合 | M1 可视 probe；只替换 FireFlowField 内部求解器 |
| 2400 珠性能不足 | 流场低于 30 Hz、频繁 GC、帧时间尖峰 | 数据池、结构化数组、空间网格、绘制批次；不得删珠或自动降质 |
| 成分图与外观不一致 | 珠子从轮廓外生成、遮罩错位 | 构建期尺寸/颜色/轮廓校验，资源拒绝加载 |
| Canvas 与 DOM 输入串扰 | 点按钮时喷火、松开后继续喷火 | 统一 InputRouter、window 级 pointerup、Playwright E2E |
| 参数过多导致反复改代码 | 调手感必须改常量或重新编译规则 | 先建配置契约；所有试玩参数集中配置并带范围 |
| 视觉随机改变结算 | 调粒子后同 seed 结果变化 | 规则和视觉使用独立随机流 |
| npm 镜像版本滞后 | 默认 registry 查询结果落后于官方，或已发布的 Phaser 4.1.0 返回 E404 | M0 先做双 registry probe；Phaser 安装显式使用官方 registry，不修改用户全局 npm 配置 |
| Phaser 小版本差异 | 4.1.0 ESM、遮罩或渲染出现明确阻塞 | M0 精确版本 smoke；有证据后再评估 4.2.x，不自动升级 |
| 音效事件风暴 | 大量珠子触发爆音或通道耗尽 | 配置化时间窗合并、最大并发和音量上限 |
| 范围膨胀 | 开始实现融合、丹方、存档或完整反应引擎 | 以第 3.2 节为门禁，新增范围先更新决策文档 |
| Web 与 Unity 浮点结果不完全相同 | 未来对照逐帧位置存在微差 | 迁移验收以语义事件、容差和不变量为主，不承诺复用 TS 源码 |

## 13. Unity 迁移准备

网页版本要沉淀的不是 Phaser 场景代码，而是以下可迁移产物：

## 14. 开发与审查闭环

每个阶段按以下顺序执行：

1. 将阶段目标拆成可验证的小任务；
2. 先补规则测试或最小可视 probe；
3. 做最小实现，不顺手重构无关代码；
4. 运行目标测试、相关回归、类型检查和构建；
5. 对涉及浏览器交互的改动运行 E2E；
6. 对涉及模拟数据布局的改动重跑 900/2400 性能场景；
7. 检查 diff、未使用代码、配置硬编码和工作树状态；
8. 在阶段验收记录中保存命令、实际输出、浏览器/硬件信息和未决项。

发现缺陷后的修复闭环遵循项目规则：

- reviewer 提供完整复现步骤、probe、实际输出与期望输出；
- 每一轮使用新的 repair agent；
- repair 先复现并把 probe 转成 RED 测试，再做最小修复；
- 修复后运行目标测试、相关回归和必要全量测试；
- 连续出现同类边界问题时，升级为 boundary inventory 审查；
- 最终完成前由主 agent 独立检查 diff、关键命令和工作树。
