## 2. 实现与冻结契约

### 2.1 固定步与应用事务

- `FixedStepClock` 固定为配置化 30 Hz，限制单帧追赶步数并独立记录 `droppedTickCount`。
- `beforePhase0(deliveryBoundaryTick)`、phase 0～10、phase 8 原子账本和 phase 10 发布沿用 application 权威边界。
- phase 3 计算流场、phase 4 规则采样、phase 5 圆障碍运动；外部可见的圆位置、流场 generation、digest、更新计数和性能原始样本只在成功 tick 提交后一起发布。
- 技术运行时使用两套 `FireFlowField` 和两套圆形 SoA TypedArray 复用缓冲。正常 tick 每次只求解一次，不在逐 tick 热路径重建大缓冲。
- 独立 probe 枚举 phase 3～10 异常：失败后外部 view、圆数组、tick、generation、digest、规则/渲染采样和 raw sample 均不变；同一 prepared boundary 重试只提交一次。
- `onTickCommitted` 属于提交后通知：外部 callback 抛错时 application 与技术运行时保持一致已提交，下一次推进进入新 tick，不重复发布旧 tick。

### 2.2 FireFlowField 与配置

- 求解器隐藏在 `FireFlowField` 接口后，采用固定网格、SoA TypedArray、借用只读 view 和确定性 tie-break。
- 支持完全矩形障碍、圆形部分障碍、障碍叠加、移动、缩小和删除后的动态重建。
- 圆覆盖子采样为配置项，默认每轴 4 点；该值能覆盖生产 900/2400 fixture 中的全部小圆，避免中心点采样导致的小圆消失和伪满格。
- 网格、求解参数、世界、火源、技术 probe、性能场景、阈值、seed、运动和 spawn area 均来自 Schema 校验的配置，不在场景代码中写死基准珠数。
- fixture 在 strict JSON 后依次经过 JSON Schema 与语义校验；spawn area 必须位于世界内且宽高不小于圆直径。
- 启动前额外校验网格物理尺寸、fixture 世界、固定 1600×900 逻辑画布和 30 Hz 性能协议相互兼容；失败显示稳定中文配置错误且不创建 Canvas。

### 2.3 浏览器技术验证台

- 提供 pillar、gap、crowd、900 珠和 2400 珠五个可直接进入的场景；crowd 使用正常大珠尺度，900/2400 仅使用独立小圆代理做性能采样，并在界面中分组标明。
- 首页默认展示由 280 个预分配粒子构成的动态火流，粒子只从底部火源生成并读取同一份已提交流场方向；切换到非火焰模式时展示层只清理一次。
- 右栏用大白话说明当前场景，并解释运动火流、灰色障碍和暗区；`prefers-reduced-motion` 下提供静态火流。
- 展示与调试支持火焰、可达区、方向、障碍、耗时和关闭；场景与模式均发布明确 active 状态。
- `window.__LIANDAN_M1__` 只暴露只读 snapshot、覆盖层选择和定时采样入口。
- Canvas 逻辑/输出尺寸为 1600×900；规则采样和渲染采样来自同一已提交 field generation。

## 6. 独立审查与修复闭环

- application/domain/simulation 修复了 phase 回调异常的 tick 快照与重试边界，并保留提交后通知的明确语义。
- FireFlow 小圆覆盖审查发现每轴 2 点会让生产 fixture 大量小圆不可见；修复为配置默认 4 点，并加入 0～1800 tick 全量圆可见证明。
- 性能样本审查补齐非空、有限、采样窗内、严格单调 timestamp，以及动态 1800 tick eligible 覆盖。
- 游戏集成审查复现 phase 8 失败后圆位置和流场 generation 半写；新运行时以双缓冲和提交时交换修复，随后独立枚举 phase 3～10 通过。
- 跨配置、spawn area、eligible 真实计数和 production fixture 行为均由 RED→GREEN 测试补齐。
- 性能 runner 审查复现端口占用时误测旧服务；修复端口独占、本次子进程 ready、随机 dist binding 和严格 fixture 自校验。
- 第二轮 runner 审查复现 TERM/KILL 无效时仍可能假 PASS；修复两阶段退出验证、stop/unlink 独立清理、`childExitedAfterCleanup` 和统一最终 outcome。最终复审未发现新的功能缺陷或假 PASS 分支。
- 火焰可读性修复先以 RED 测试证明首页缺少独立火焰模式与场景说明，再加入预分配流场粒子、图例和大白话说明；视觉审查随后复现预热粒子同步堆积，修复后火源带粒子由 80/280 降为 25/280。
- 发布复审复现关闭火焰后 `data-fire-frame` 残留且每帧重复清理；新 repair 轮次改为离开火焰时只清一次，并补齐首页、关闭、减少动态效果和 digest 的 Chrome/Edge 回归。粒子轨迹 probe 证明当前两股火绕柱后保持平行，因此用户说明改为准确的“从左右绕过后继续向上”，未伪造脱离流场的汇合动画。

## 8. 正常珠视觉跟进

根据 2026-07-14 的画面反馈，`crowd` 正常珠由半径 48px 的圆形表现调整为半径 32px 的流场碰撞代理加 64px 高水滴表现；数量保持 8 颗，900/2400 性能场景继续使用半径 6px / 4px 的小圆代理。Canvas 额外发布 `data-pearl-renderer` 与 `data-pearl-radius`，Chrome / Edge E2E 会同时验证正常水滴珠和性能小圆没有互相污染。

随后复现了火焰遮挡把命中的 20px 流场格整格清空，导致水滴周围出现方洞的问题。正常技术场景现改为在 320×180 热场分辨率复用精确几何遮罩：圆形珠遮挡半径为碰撞半径的 0.82 倍，边缘 4px 柔化；矩形炉体同样按真实边界遮挡。求解器仍使用原有圆形子采样碰撞，900/2400 性能场景仍走原有流场网格遮挡路径，因此本轮只修最终画面合成，没有改写性能门禁的模拟口径。Canvas 发布 `data-fire-occlusion="precise-geometry"` 或 `"flow-grid"`，E2E 固定两条路径不会串用。

本轮 `npm run check` 为 27 个测试文件、294 项通过，Chrome / Edge E2E 为 36 项通过；浏览器视觉证据见 [`64px 水滴珠验收报告`](../output/browser-qa/droplet-pearls/report.md) 与 [`圆形挡火验收报告`](../output/browser-qa/rounded-occlusion/report.md)。
